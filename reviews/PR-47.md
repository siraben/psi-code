## Project intent

Refactor `psi --tui` from a full-frame absolute-positioned renderer to a component-based, line-diff renderer. Lua composes width-bounded line arrays through new `tui_component.lua` + `tui_components/{chrome,markdown}.lua`; `tui_renderer.lua` diffs lines against a previous-frame cache and writes only changed rows between BSU/ESU sync markers via `psi.stdout_write`. Full redraw remains the conservative fallback for first paint, dimension change, forced clear, and missing writer.

## Should fix

### Single-hyphen delimiter rows are accepted as GFM tables
`lua/psi/tui_components/markdown.lua:174`

The separator-cell pattern is `^:?-?%-+%s*:?$`. The `%-+` quantifier matches one-or-more hyphens, so a single `-` (or `:-`) per cell is treated as a valid GFM separator. GFM requires **three** hyphens minimum per column. Confirmed by direct test: input `| A | B |\n| - | - |\n| x | y |` renders as a boxed table instead of paragraph text.

→ Tighten the pattern to require `^:?%-%-%-+%s*:?$` (three or more hyphens), with the leading `:` and trailing `:` optional. Add a smoke test on `| - |` to lock this in.

### Double-backtick code spans break table rows
`lua/psi/tui_components/markdown.lua:110–113`

`parse_cells` toggles `in_code` on every single backtick byte (`elseif ch == "`" then in_code = not in_code`). For double-backtick spans `` ``a|b`` `` the four backticks flip `in_code` four times, leaving it `false` at the pipe between `a` and `b`. The pipe is then treated as a cell delimiter; `is_table_row` rejects the row for column-count mismatch; the renderer emits a header-only table with the row leaking out as raw text. Single-backtick code spans work correctly.

→ Tokenize backtick *runs* and only close on a matching-length run. The pattern is "open with N backticks, close with the next N+ backticks". Pi-mono's markdown component does this; the existing `markdown.lua` doesn't need to change.

### Component / transcript caches hold stale ANSI after theme switch
`lua/psi/tui_components/markdown.lua:523–541` and `lua/psi/tui_runtime.lua:667–668`

`render_component` caches fully-styled lines keyed on `(text, prefix_first, prefix_rest, width)`; the cached strings embed ANSI bytes resolved through `psi.ansi.set_code_map`. `psi.theme.use` → `apply` → `ansi.set_code_map` is reachable at runtime via `/reload` (`commands.lua:389–390` → `theme.apply_configured`). Neither the component cache, nor `entry.render_cache_lines` in `tui_runtime.lua:667–668`, is invalidated on theme change. After a runtime theme switch the transcript renders existing assistant entries with the previous theme's SGR codes until their underlying text is rewritten.

The cross-validator noted that `markdown.render_line`'s pre-existing per-line cache (`lua/psi/markdown.lua`) has the same root issue and is also unkeyed by theme — so the staleness pattern existed before this PR. The new component cache and `entry.render_cache_lines` *extend* the cached surface area without addressing the underlying problem.

→ Best fix wires a global theme-change hook: on `theme.use` / `apply_configured`, walk transcript entries and call `markdown_component:invalidate()` + clear `render_cache_lines`, then `markdown.clear_render_cache()`. Alternatively key all three caches on a theme generation counter incremented inside `theme.use`.

## Architecture observations

- **`tui_text.visible_width` does not handle East Asian wide characters or emoji ZWJ sequences.** Pre-existing behavior carried into the new helper; not a regression. Worth a follow-up since the new component layer formalizes width as a contract.
- **Cursor marker is in-band.** `CURSOR_MARKER = ESC _psi:c BEL` (an APC sequence) is inserted into the input line and stripped on `extract_cursor` via literal `:find`. Pasted content containing the same APC sequence would be silently consumed as a cursor marker. The runtime's `sanitize_terminal_text` strips APC sequences from incoming bytes, so the practical attack surface is contained, but the assumption deserves a one-line comment in `tui_renderer.lua`.
- **`tui_components/markdown.lua` is 563 lines in one file** (parser, GFM separator detection, column allocator, wrap, render, cache). A `markdown_table.lua` split would shrink the surface and let the parser be unit-tested in isolation. Not blocking.

## Rejected during cross-validation

- **CA1 (Codex)** — Differential renderer ignores `raw_ansi` capability gate. Rejected: pre-existing. The full-frame path at `tui_renderer.lua:177–186` calls `psi.tui_render_frame`, which (per `src/lua/vm.c`) unconditionally emits CSI escapes regardless of `raw_ansi`. The diff path is no worse than the existing full path, and TUI compile-time gating already prevents these bytes from reaching a host that can't handle them; the runtime `raw_ansi` override has never been enforced at this layer.
- **CB1 (Codex)** — Markdown component cache ignores theme changes. Rejected as a duplicate of CMP1's wider claim and because `markdown.render_line` already had the same staleness pattern pre-PR; the issue is real but the regression is captured by CMP1.
